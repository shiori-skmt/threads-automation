# Threads × 楽天アフィリエイト 自動投稿パイプライン

このファイルは、スケジュール実行されるClaude Codeセッションが**会話の記憶を一切持たない状態**で読む指示書です。ここに書いていないことは分からない前提で、省略せず記載しています。

作業ディレクトリ: このリポジトリ(クローン済み)の `rakuten-threads-bot/` フォルダ。パスは環境によって変わるため、常に「リポジトリのルートからの相対パス」で扱うこと(例: `rakuten-threads-bot/state/...`)。

## 0. 認証情報の読み込み(クラウド実行専用)

**このパイプラインはクラウド上のスケジュール実行(routine)専用。ローカルの`.env`は存在しない。** 以下の値は、このタスクを起動したプロンプト本文の中に直接書かれている(このセクションの下、または末尾の「認証情報」ブロックを探すこと):

- `RAKUTEN_APP_ID`
- `RAKUTEN_ACCESS_KEY`
- `RAKUTEN_AFFILIATE_ID`
- `THREADS_ACCESS_TOKEN`
- `THREADS_USER_ID`
- `RAKUTEN_REFERER`(デフォルト `https://threads.com/`。**`threads.net` ではなく `threads.com` が正しいドメイン**)

プロンプト中の値を使って、作業開始時に一度だけ環境変数としてexportする:
```bash
export RAKUTEN_APP_ID="..." RAKUTEN_ACCESS_KEY="..." RAKUTEN_AFFILIATE_ID="..." THREADS_ACCESS_TOKEN="..." THREADS_USER_ID="..." RAKUTEN_REFERER="https://threads.com/"
```
(値そのものはこのファイルには書かれていない。呼び出し元のタスクプロンプトに書かれている値を使うこと)

**すべての楽天APIリクエストに、HTTPヘッダー `Referer: ${RAKUTEN_REFERER}` と `Origin: ${RAKUTEN_REFERER}`(末尾スラッシュなし)の両方を付与すること。** どちらか一方でも欠けると403エラーになる(検証済み。Refererのみだと `REQUEST_CONTEXT_BODY_HTTP_REFERRER_MISSING`、ドメインが許可リストと不一致だと `HTTP_REFERRER_NOT_ALLOWED` になる)。

## 0.3. 「今日の日付」の確定(JST基準・必須)

**このパイプライン内で「今日」「実行日」「対象日」という言葉が出てきたら、すべて日本時間(JST, UTC+9)の日付を指す。** クラウドの実行環境はUTCで動いているため、システムの生の日付やモデル自身の「今日」の認識をそのまま使うと、JST早朝(0時〜9時台)は前日の日付になってしまう(検証済みの不具合。古い下書きを「今日の分」として再提示してしまう原因になっていた)。

作業開始時に一度だけ、以下のコマンドでJST日付を取得し、以降このパイプライン内の「今日の日付」「対象日」はすべてこの値を使うこと(UTCの生の日付やモデル自身の推測日付は使わない):
```bash
TZ=Asia/Tokyo date +%Y-%m-%d
```

## 0.5. 状態の永続化(git pull/push、クラウド実行専用・必須)

**このパイプラインはクラウドの独立したセッションとして毎回新しく起動し、リポジトリを都度クローンする。`state/` 配下のファイルは、前回までの実行結果をgit経由で引き継ぐ唯一の手段。** このルールを省略すると、ジャンルローテーションや投稿タイプの判定、二重投稿防止が壊れる。

- **作業開始時(何かを読む前に必ず)**: リポジトリのルートで `git pull` を実行し、最新のstateを取得する
- **`state/` 配下のファイルを1つでも作成・変更・移動したら、その都度(役割の終わりではなく、その場で)**: リポジトリのルートで以下を実行してコミット・pushする
  ```bash
  git add rakuten-threads-bot/state
  git commit -m "update state: <何をしたか一言>"
  git pull --rebase
  git push
  ```
  (他方のアカウント用routineが同時に動いて競合する可能性があるため、pushが失敗したら `git pull --rebase` してから再度 `git push` する)
- コミット対象は `rakuten-threads-bot/state/` 配下のみ。`PIPELINE.md` や `MORNING_GREETING.md` 自体は書き換えない
- git操作(add/commit/pull/push)は毎回シンプルな単体コマンドで行うこと。複数を `&&` で1行に詰め込みすぎない

## 1. 全体の仕組み: 1日2枠(昼12:00・夕方18:00)、当日の勤務時間中に確認して予約投稿

この投稿枠は「昼」「夕方」の1日2枠。**投稿は決まった時刻に自動で行い、内容の確認はユーザーが仕事中にできる時間帯に済ませておく**運用のため、以下のように役割が分かれている(それぞれ独立したスケジュールタスクから呼ばれる):

- **ドラフト作成タスク(毎日9:00頃実行。昼枠・夕方枠とも)**: 「実行日と同じ日」(=対象日)の対象枠のドラフトを作り、チャットに提示して承認を待つ。**投稿はしない**
- **リマインドタスク(枠ごとに別時刻。昼枠は11:00頃、夕方枠は17:00頃)**: 該当枠のドラフトがまだ未承認なら、投稿時刻が近づいたタイミングで一度だけ内容を再掲してリマインドする
- **投稿タスク(枠ごとに毎日実行。昼枠は12:00、夕方枠は18:00)**: 承認済みの「今日・その枠」のドラフトがあれば、それをThreadsに投稿する。**新規に文章を作らない。承認済みのものを投稿するだけ**。未承認なら見送った旨をユーザーに知らせる

このファイルの2節以降(役割1〜6)は、どちらの枠のドラフト作成タスクからも共通で使う手順。「対象枠」(昼/夕方)と「対象日」(実行日と同じ日)は、呼び出し元のタスクの指示で渡される。

朝6時のあいさつ投稿だけは確認のタイミングが異なる(前日15:00に作成、当日6:00に投稿)。そちらの詳細は `MORNING_GREETING.md` を参照。

**シェルコマンドの書き方の制約**: 投稿処理・状態確認・状態ファイル(state/配下のjson)の更新で、以下を避けること。Bash上でPython等のスクリプトを生成して実行する、`awk '{...}'` のような一行コマンド、その他ブレース `{ }` とクォートを組み合わせた一行コマンド全般――これらは「難読化っぽいパターン」として自動モードの安全確認に引っかかり、`bypassPermissions` 設定でも止まってしまう。代わりに以下のシンプルなコマンドだけを使うこと:
- ファイルの存在確認: `ls`, `test -f`, `[ -f path ]`
- 文字列・行数の確認: `grep -c`, `wc -l`, `wc -c`(トークンの中身を見ずに文字数だけ知りたい場合は `wc -c` を使う。`awk`は使わない)
- JSON値の取り出し: `jq -r .id` のような単純なフィルタ(ブレースを含む複雑なjqプログラムは避ける)
- ファイル移動: `mv`
- 投稿: curlを直接実行し(`--max-time 20` を付ける)
- jsonファイルの読み書き: Read/Edit/Writeツールを直接使う(Bash+スクリプトで読み書きしない)
- **文字数チェック・リンク照合は、sedやgrepで投稿ごとに切り出して数える複雑な一行コマンドを作らないこと。ドラフトファイルはReadツールで開き、目視で文字数とリンクを確認すれば十分(1投稿あたり数文のカジュアルな文章なので、正確な文字数カウントコマンドは不要)。Bashで確認する場合も、ファイル全体に対して `wc -m` を1回実行する程度に留める**

商品紹介やアフィリエイトを含まない、6時の「おはよう」あいさつ投稿は完全に別枠。そちらは `MORNING_GREETING.md` を参照(このファイルの対象外)。

## 1.5. 【2026-10-06〜】1日3枠(昼12:00・夕方18:00・夜21:00)・全枠PR型・体験談メイン

アフィリエイトリンクを1日最低3件にするため、投稿枠を「昼(noon)12:00」「夕方(evening)18:00」に加えて**「夜(night)21:00」**を追加し、3枠すべてをPR型にする。朝6:00のあいさつ(PRなし)は従来どおり。この節は他の節より優先する。

- **枠の名前**: ファイル名・履歴の`slot`は `noon` / `evening` / `night`。ドラフト作成は9:00頃(3枠とも)、投稿は12:00 / 18:00 / 21:00。13節・14節の手順は、夜枠も同じ(対象枠=night、投稿時刻=21:00、リマインドは20:00頃)
- **【2026-10-06〜】PR型の1件目に画像は付けない**: 2件目のリンクのOGPカードに商品画像が出るため、同じ画像が並んでしまう。ドラフトの「画像」「image_url」は不要(書かない・使わない)。投稿は常にテキストのみ(`media_type=TEXT`)
- **投稿タイプ**: 昼・夕方・夜の3枠は**常にPR型**。3節の判定(3連続回避・比率調整)はスキップし、そのまま4節へ進む。ただし商品が見つからない場合(4節の最後)に限り、その枠だけつぶやき型にフォールバックしてよい(その場合もリンクを入れられない旨をユーザーに伝える)。履歴には実際に投稿した`type`を記録する
- **PRが増える分、広告感を抑える(体験談メイン)**: 7節のPR型の文章は、商品の説明・宣伝ではなく**一人称の体験談を主役**にする
  - 主役にするのは「使った・試した・選んだ理由・使っていて気づいたこと・困ったことが変わった場面」。具体的な場面(いつ、どこで、何に困っていたか)を1つ入れる
  - **良くない点・合わなかった点・注意点を1つ正直に入れる**(例: 匂いが強い、値段は高め、サイズに注意)。褒めるだけにしない
  - 「おすすめ」「買って」「最高」などの勧誘表現・断定的な効果効能は使わない。薬機法・景品表示法のルールは従来どおり
  - リンクと「PR」表記は2件目(リプライ)に入れる(2件以内ルールは従来どおり)
- **【重要】実際に使っていない商品を、使った体験として書かない**(ステマ・優良誤認になる)。体験談として書いてよいのは、`real_reviews.md`に載っている商品(飼い主が実際に使ったもの)と、ユーザーが指示した体験だけ。それ以外の商品は「気になってる」「検討中」「商品ページには〜と書かれていた」という立場で書き、使った感想は一切書かない。`real_reviews.md`の商品は、投稿済みでなければ優先して使う

## 1.6. 【2026-10-14〜】追加ルール(PR投稿の「5と0のつく日」一言/犬用投稿の対象拡大)

### (a) 5と0のつく日の一言(PR型の全投稿・必須)
- JST基準の日付(0.3節)の**日(day)が 5・10・15・20・25・30 のいずれか**の日は、PR型の1件目(本体)の**冒頭**に「今日は楽天の5と0のつく日、お買い物日和🛍」のような一言を入れる(毎回同じ文言にせず、言い回しは揺らしてよい。例:「今日は5と0のつく日!楽天でお買い物日和🛍」)
- 断定してはいけない表現: 「お得」「安い」「最安」「ポイント何倍」など、条件や金額に言及する言い方(景品表示法対応)。あくまで「お買い物日和」程度の一言にとどめる
- 31日がある月でも、5と0のつく日は「5, 10, 15, 20, 25, 30」のみ(31日は対象外)
- 一言を入れた分は、本文全体の文字数(500字以内)とチェッカー(10節)の「PR表記」の確認も通常どおり行う

### (b) 犬用の投稿の対象を広げる(ゆずアカ・わんこ要素のある投稿)
- **割合の目安: 犬用品 2 : 人間用の柴犬グッズ 1**(ゆずアカのPR投稿全体で。連続して人間用ばかり・犬用ばかりにならないよう、直近の投稿(`posted_items.json`/`posted_drafts/`)を見て調整する)
- 犬用の投稿は、**犬用品だけに限らず、人間が使うもので「柴犬」が商品名・説明に入っているもの**も対象にする(例: 柴犬のTシャツ、柴犬のぬいぐるみ・抱き枕、柴犬柄のトートバッグ・スマホケース・マグカップ・ステッカー)
- 人間用の柴犬グッズも、使っていない商品は「気になってる」の立場で書く(体験談の作り話は禁止。1.5節と同じ)
- 商品検索は「柴犬 Tシャツ」「柴犬 ぬいぐるみ」のようなキーワードで行ってよい。人間用グッズはレビュー件数が少ないことがあるため、レビュー20件以上・評価4.3以上を目安に緩めてよい(件数が少ない場合は、投稿文にそのまま件数を書く)

## 1.8. 【2026-10-16追加】PR投稿1件目に価格を入れる

- PR型の1件目(本体)に、商品の価格を入れる。レビュー行がある場合は、同じ行の先頭にする(例:「1,290円、レビュー504件で★4.73」)。レビュー行を省略する場合は、価格だけの行を末尾(ハッシュタグの前)に置く。
- 価格は、ドラフト作成時に楽天商品検索APIで取得した `itemPrice`(税込表示)の数字をそのまま書く。ドラフトの「商品情報」の価格は「(投稿文に載せる)」と記す。
- 「お得」「安い」「格安」「最安」「〜円オフ」「セール」「期間限定」など、価格が有利だという断定や強調の言い回しは、これまでどおり禁止(景表法)。数字だけを事実として書く。
- 商品名・リンクを書く2件目には、価格を書かない。

## 1.9. 【2026-10-17追加】参考アカウント(@chami_kaimonokiroku)のPR投稿から取り入れる型

参考にした2投稿の分析。反応の数字(閲覧・いいね)は入手できていないため、「効果が確認された型」ではなく「試してみる型」として扱う。使った投稿は計画CSVの備考に「型B」「型C」と書き、あとで反応分析(10/8〜の集計と同じ方法)で比べる。

**参考投稿の特徴**
- (1)商品PR投稿: 冒頭に驚きのフック(「えっ、これがクーポンで2,980円!?」)→悩んでいる人への呼びかけ(「寝室やデスクに置く加湿器を探してる人、これ見て」)→「✔️」の箇条書きスペック7項目→「コンパクトだから置きやすそう」の一言→「要チェック!」→価格の念押し→条件確認の誘導(「👇」)→【PR】とリンク→ハッシュタグ4つ(商品名・用途・#便利グッズ・#楽天アフィリエイト)。1投稿の中にリンクまで入れている。短い行を多用し、絵文字(😳✨🫧🥹🌿)が多い。
- (2)「情景想像型」の解説投稿: 「(場所)で、これ持ってる人がいたら(反応)」の13例。コツは「商品をおすすめするのではなく、読んだ人の頭に具体的なシーンを浮かばせる」「『便利そう』『可愛い』で終わらず『思わず二度見する』『どこで買ったか聞きたくなる』と、見た人のリアクションまで書く」こと。

**取り入れる型(PR型の1件目。下の【2026-10-21更新】のとおり、型Bを1日2件まで増やす)**
- **型B: 情景想像フック型**。1行目を「(場所)で、これ(使って)るママ/人がいたら、(反応)」にする。場所はペルソナの生活圏から選ぶ(一般: 保育園のお迎え、公園のベンチ、スーパーのレジ待ち、電車の中 等。ゆず: ドッグランの入口、朝の散歩道、動物病院の待合室、柴友さんとの立ち話 等)。反応は「二度見する」「どこのか聞きたくなる」「思わず探しちゃう」など。**「他人がそれを使っていたら」という仮定の書き方に限る。自分が使った、見かけたという事実を作らない**(実使用でない商品を使った話にしない、という従来のルールは変えない)。
- **型C: 箇条書きスペック型**(家電・ガジェット系の商品のみ)。「✔️」で3〜5項目に絞る(参考投稿は7項目だが、長いと読まれにくい)。箇条書きのあとに、自分の事情の一言を必ず入れる(8.6節の1)。
- **呼びかけ**: 型B・Cの冒頭または末尾に「〜を探してる人」「〜が気になる人」と対象を呼びかけてよい。
- **誘導の一言**: 末尾に「詳細は返信のリンクから👇」を付けてよい(2件目のリンクへ誘導する)。型B・Cでのみ。
- **ハッシュタグ**: 型B・Cに限り、商品カテゴリ・用途のタグを2〜3個、末尾に付けてよい(例: #加湿器 #乾燥対策)。**#楽天アフィリエイトなど、広告であることを示すタグは付けてよい。PR表記(2件目の「PR」)は従来どおり必須**。型A(従来の型)は、8.6節の6のとおり、柴犬グッズの1個まで。

**【2026-10-21更新】型の比率と書き方の追加ルール**(ユーザーの指示)
- **型Bを増やす**。1日3件のPRのうち、**型Bを2件**、型CまたはAを1件にする(型Cは、家電・ガジェット系の商品があるときだけ。無ければ型A)。
- **型Cは、家電・ガジェットに限らず、スペックを3〜5項目に並べられる商品なら、何にでも使ってよい**(2026-10-22更新。ユーザーが「チェック形式」を増やしたいとの指示)。1日3件のPRのうち、型Cを1〜2件、型Bを1〜2件にしてよい。
- **型Cの締めは、改善・前向きな方向の文で終える**。不満・悩みで終わらせない。悪い例:「空気がカラカラで、手もガサガサ💦」で終わる。良い例:「これから本格的に乾燥する季節だから、いまのうちに部屋の湿度を整えておきたい」「デスクの足元が楽になったら、勉強がはかどりそう」。悩みを書くなら、その後に必ず「だから〜したい/〜してみようかな」と続ける(8.5節の「願望を決意に変える」と同じ)。
- **商品で悩みが治る・改善するように読める書き方はしない**(薬機法・景表法)。例:「卓上加湿器で手荒れが治る」「サーキュレーターの乾燥対策に加湿器で手がしっとり」のように、**体の不調(手荒れ・肌荒れ・かゆみ 等)と商品を原因→解決で結びつけない**。加湿器は「部屋の乾燥対策」までにとどめ、手荒れの話は別の文にして、商品と結びつけない。

**取り入れないもの(法令・品質上の理由)**
- 「えっ、これがクーポンで◯◯円!?」のような、クーポン価格の驚きを煽る言い方。クーポンの有無・条件・期間を確実に確認できない限り、クーポン価格は書かない(景表法の有利誤認のおそれ)。価格の事実は1.8節のとおり、通常の販売価格の数字だけを書く。
- 「超静音」「たっぷり」「手軽」などの強い言い切り。商品ページの記載にあるスペックを、数字や記載のとおりに書く(例:「静音設計と書かれていた」)。効能の断定は従来どおり禁止。
- 「いいねと再投稿をしてくれたらDMで送る」などの、反応を求める誘導。このアカウントでは行わない。
- 「絶対」「必ず」「どこよりも」などの強調。

## 7. 役割4: 投稿ライター

### PR型の場合

切り口担当が出した案から1つを選び、連続投稿を書く。

**PR型のスレッドは必ず2件以内(本体1件+リプライ1件)に収める。** Threadsの仕様上、リプライが2件以上になると「他N件の返信を見る」のように畳まれてしまい、PRリンクを含む最後の投稿が読者から見えにくくなるため、3件以上のスレッドにしない。

**型は以下3パターンから、ジャンル・商品の性質に合うものを選ぶ(固定運用にしない。いずれも2件構成)**:

- **教育的長文型**(@rino_dog_life参考、ペット・キッズ向き): 1件目で悩み提起、2件目で共感・詳細解説+解決策としての商品紹介をまとめ、末尾に商品名・リンク・PR表記
- **省エネ・curiosity型**(@popo.biyou参考、美容向き): 1件目は商品名を出さない一言フックのみ。2件目リプライで「楽天 pr」+リンクだけ
- **誇張フック+リスト型**(@benri_na_kurashi参考、キッチン・生活雑貨向き): 「ブランド名や特徴+驚き」の一言フック→リプで理由+「▶リンク PR」

**執筆5原則(すべての型に共通)**:
1. 商品紹介より先に「悩み」から入る
2. 「これ便利!」ではなく「これで〇〇が楽になった」のように、変化・結果で語る
3. どんな人におすすめなのかを明確にする
4. 商品写真だけでなく、使用シーン・使用イメージが伝わる書き方にする
5. 「買ってほしい」気持ちを前面に出しすぎない

ゴールは「売る」ことではなく、読み手に「これ、自分にも必要かも」と思ってもらうこと。

「PR」または「#PR」表記は必須(景品表示法のステマ規制対応)。

### つぶやき型の場合

商品紹介を一切含まない、雑談・日常投稿を書く。

**投稿数は内容量で決める。基本は1件で書き切る。** つぶやき型はPR型のcuriosity型(意図的に1件目で焦らして2件目で回収する構成)とは目的が違う。無理にスレッド化しても読者側に利点がないので、複数件に分けるのは「本当に1投稿(500字)に収まらない」場合か「小出しにする明確な演出意図がある」場合のみにする。

**参考にするトーン:**
- `@rino_dog_life`の非PR投稿(しつけ知識、犬との日常の気づき、飼い主としての実感)
- `@azarachi_mama`の私生活寄りの一言(今日あった出来事、子どもの様子、ちょっとした気持ちの吐露)

**テーマの選び方**: ペルソナ(30代・子育て中・犬を飼っている女性)として自然な範囲で、以下のような切り口からその日の気分でランダムに1つ選ぶ:
- 犬・子育ての日常でふと感じたこと(あるある、気づき、ちょっとした成長エピソード)
- 季節・天気・時事に絡めた軽い雑談(**天気ネタにする場合は、投稿前に必ず東京の実際の天気を確認し、内容と齟齬が無いようにする**。例: `curl -s "https://api.open-meteo.com/v1/forecast?latitude=35.6895&longitude=139.6917&current_weather=true"` で現在の天気・気温を取得できる。確認できない/合わない場合はこのテーマを避ける)
- 育児や家事の中の小さな工夫や失敗談(特定商品名は出さない)
- 「わかる〜」と共感してもらえるような、飾らない一言つぶやき

**厳守事項(PR投稿との誤認を避けるため)**:
- 商品名・ブランド名・アフィリエイトリンクを一切含めない
- 「PR」「#PR」表記を付けない(つけると読者が誤解する)
- 購入や来店を促すような表現(「▶リンクはこちら」等)を使わない

**自然さを損なう表現を避ける**:
- 子どもや家族を指す二人称に「あなた」を使わない(不自然)。子どもは「ムスメ」と表記する
- ペット(犬)の反応などを、実際にその場にいたか怪しい形で描写に足さない(例: 「犬も一緒に首をかしげてた」のような、話を面白くするためだけの作り話感が出る描写)。事実として自然に言える範囲に留める

**文末・改行ルールはPR型と共通(3アカウントに共通する特徴。必ず反映すること)**:
- **文末には必ず絵文字か記号(「…」「〜」「!」「?」)を入れる。** 「。」で言い切らないのはもちろん、体言止めなど何もつけずに終わらせることもしない。比率の目安は**絵文字7割・記号3割**程度(毎回絵文字に頼りすぎない)
- **改行・空行の入れ方**: 1文ごとに機械的に空行を入れるのではなく、同じ話の流れ(同じ出来事・同じ時間軸について考えている間)の文は改行だけでまとめる。**別の出来事・時間・場面に移る瞬間だけを「文脈の切れ目」とし、そこにだけ空行を入れる**(単に考えを続けている・理由を補足しているだけの文は切れ目にしない)

**文脈の切れ目をまたぐときの前置き(つぶやき型のみ)**: 空行を挟んで新しい話題に移るときは、唐突にならないよう「そういえば」「あ、」「でもさ」「そうそう」のような自然な接続語・前置きを文頭に添える(毎回同じ言葉を使い回さない)。**PR型は文脈が大きく変わらない構成なのでこの前置きルールは適用しない**

## 8. 役割4.5: 人間らしさ推敲役(すべての投稿共通・必ず実施)

役割4が書いた文章は、この時点ではまだ「AIが書いた文章」っぽさが残っていることが多い。投稿ライターの執筆段階と、書き終えた後の推敲段階の両方で、以下を徹底する。

**執筆段階で意識すること:**
1. **説明しすぎない。** 読者が文脈から理解できる部分は、あえて言葉にせず余白を残す(全部言い切らない)
   - ただし、余白を残すことと主語・目的語を省くことは別。**誰が何をしたか(主語・目的語)が読み取れなくなるほど省くのは禁止**。「〜の途中で呼んだ」「〜してくれた」のように読者が『誰が?誰に?』と迷う文は、主語を補うか具体的な場面に言い換える(実例: 「ブラッシングの途中で呼んだら来てくれた」は誰のブラッシングか不明で差し戻しになった)
   - **【2026-10-06追加】不自然さを生む5つのパターンを避ける**(実例: 「今日もゆずに起こされました、毎回同じ時間に鼻先でツンツンしてくるのが地味に効くんですよね😅 そういえば…ひと伸び…見てるだけで笑っちゃいます😂」が不自然と指摘された)

## 11. ドラフト保存とユーザーへの提示(ドラフト作成タスクの最終ステップ)

全てのチェックを通過したら:

1. `state/pending_drafts/{対象日}-{対象枠}.md` (例: `2026-09-26-noon.md` / `2026-09-26-evening.md`) に以下を保存する:
   - 冒頭に「投稿予定日時: {対象日} {12:00 または 18:00}」「投稿枠: 昼またはevening」「投稿タイプ: PR型またはつぶやき型」を明記
   - PR型のみ: ジャンル・商品名・商品コード(itemCode)・価格・画像URL・affiliateUrl
   - 生成した連続投稿文(投稿ごとに番号を振る)
   - チェッカー役の確認結果
2. ユーザーにチャットで内容をそのまま提示し、「これでOKか、修正したい点はあるか」を尋ねて**このセッションは終了する(この時点では絶対に投稿しない)**

## 12. 承認後のキュー登録(ユーザーがOKを出した時に実行)

このセクションは、ユーザーが `state/pending_drafts/` のドラフトに対して「OK」または修正指示を出したときに(スケジュール実行かどうかに関わらず、その場で会話の続きとして)実行する。**投稿はまだしない**

1. 修正指示があれば、それを反映してから進める
2. `state/pending_drafts/{対象日}-{対象枠}.md` を `state/approved_drafts/{対象日}-{対象枠}.md` に移動する
3. ユーザーに「{対象日} {12:00または18:00}に投稿されるようキューに登録しました」と報告する

## 13. 投稿タスク(枠の時刻になったら実行。昼枠は毎日12:00、夕方枠は毎日18:00)

1. 今日の日付・対象枠に一致するファイル `state/approved_drafts/{今日の日付}-{対象枠}.md` があるか確認する
2. **無ければ**、`state/pending_drafts/{今日の日付}-{対象枠}.md` が残っていないか確認し、以下のように知らせて終了する(新規に文章を作ったり投稿したりはしない):
   - pendingファイルが残っている場合:「今日{対象枠}分の投稿はまだ承認されていなかったため見送りました。次回は9:00のドラフト提示時、またはリマインド(昼枠11:00/夕方枠17:00)の時点でOKをお願いします」
   - pendingファイルも無い場合:「今日{対象枠}分のドラフトが作成されていなかったため見送りました」
2.5. **天気ネタの再確認(投稿直前・必須)**: 承認済み本文に天気・気温・季節感の言及(晴れ/雨/曇り/暑い/涼しい/上着/傘/洗濯物など)がある場合、投稿直前に東京の実況・当日予報を取得して照合する:
   ```bash
   curl -s --max-time 20 "https://api.open-meteo.com/v1/forecast?latitude=35.6895&longitude=139.6917&current_weather=true&daily=weather_code,temperature_2m_max,precipitation_probability_max&timezone=Asia%2FTokyo&forecast_days=1"
   ```
   本文と食い違う場合(例: 「曇り」と書いたが晴れ)は**投稿せず**、食い違いの内容をセッションの最終メッセージに明記して終了する(勝手に書き換えて投稿しない。ユーザーの修正承認を待つ)。取得に失敗した場合は、`--max-time 15` で最大3回まで再試行する(各回を独立したBash呼び出しにする)。それでも取得できない場合は、本文の天気表現が**気温・降水確率などの数字や、晴れ/曇り/雨の断定を含まない、あいまいな書き方**(例: 「あたたかくなりそう」「朝はひんやり」)であれば、そのまま投稿してよい。数字や断定を含む場合は投稿せず見送る。
3. あれば、`.env` を読み込み、Threads Publishing APIで連続投稿する。**すべてcurlコマンドを直接実行すること。投稿処理をPythonなどのスクリプトファイルに書き出して実行する方法は使わないこと**(スクリプト内の `{変数}` のようなブレース+クォートの組み合わせが「難読化っぽいパターン」として自動モードの安全確認に引っかかり、バイパス権限モードでも止まってしまうため)。**さらに、1回のBashツール呼び出しに複数のcurl・sleep・jqなどを`;`や`$()`でつなげて詰め込まないこと。「コンテナ作成のcurl」「creation_idの取り出し」「公開のcurl」「idの取り出し」は、それぞれ独立したBashツール呼び出しに分ける**(1つのコマンドにまとめるほど安全確認に引っかかりやすくなるため)。curlには通信ハング防止のため `--max-time 20` を付ける。投稿が中断・再開された場合は、投稿前に `GET https://graph.threads.com/v1.0/{THREADS_USER_ID}/threads?fields=text&limit=5&access_token=...` のような読み取り専用のcurlで自分の最新投稿を確認し、すでに投稿済みでないか(重複投稿防止)を目視で確認してから投稿する:
   - **PR型・1件目(画像なし・テキストのみ。2026-10-06〜)**: 2件目のリンクのOGPカードに商品画像が表示されるため、1件目に画像を付けると同じ画像が並んでしまう。1件目に画像は付けない:
     ```
     POST https://graph.threads.com/v1.0/{THREADS_USER_ID}/threads
       ?media_type=TEXT&text={1件目の本文}
       &access_token={THREADS_ACCESS_TOKEN}
     ```
     → 返ってきたJSONから `id`(creation_id)を取り出す。JSON応答からの値の取り出しは `jq -r .id` を使うこと(例: `CID=$(curl ... | jq -r .id)`)。Pythonなど別言語のワンライナーやヒアドキュメントは使わない。取り出したcreation_idを使って公開:
     ```
     POST https://graph.threads.com/v1.0/{THREADS_USER_ID}/threads_publish
       ?creation_id={creation_id}&access_token={THREADS_ACCESS_TOKEN}
     ```
     → 公開された投稿の `id` を(同じく `jq -r .id` で)控える(次の投稿の `reply_to_id` に使う)
   - **つぶやき型・1件目(画像なし、テキストのみ)**:
     ```
     POST https://graph.threads.com/v1.0/{THREADS_USER_ID}/threads
       ?media_type=TEXT&text={1件目の本文}
       &access_token={THREADS_ACCESS_TOKEN}
     ```
     → 同様に `threads_publish` で公開し、`id` を控える
   - **2件目以降(共通、テキストのみ、直前の投稿への返信として連結)**:
     ```
     POST https://graph.threads.com/v1.0/{THREADS_USER_ID}/threads
       ?media_type=TEXT&text={本文}&reply_to_id={直前の投稿ID}
       &access_token={THREADS_ACCESS_TOKEN}
     ```
     → 同様に `threads_publish` で公開
4. 投稿成功後、以下の状態ファイルを更新する。**必ずRead/Editツール(またはWriteツール)で直接編集すること。Bash+Python等のスクリプトでJSONを読み書きしないこと**(スクリプト内のブレース+クォートの組み合わせが「難読化っぽいパターン」として自動モードの安全確認に引っかかり、バイパス権限モードでも止まってしまうため):
   - PR型のみ: `state/posted_items.json` の `posted` 配列に itemCode を追記、`state/genre_rotation.json` の `last_genre_key` を今回使ったジャンルに更新
   - 共通: `state/post_type_rotation.json` の `history` に `{"date": "今日の日付", "slot": "noonまたはevening", "type": "prまたはtsubuyaki"}` を追記する(14件を超えたら古いものから削除して直近14件を維持)
   - `state/approved_drafts/{今日の日付}-{対象枠}.md` を `state/posted_drafts/` に移動(これはBashの`mv`コマンドでよい。ファイル移動自体はブレース+クォートの組み合わせが無いため問題ない)
5. ユーザーに投稿完了を報告する
6. 投稿に失敗した場合(トークン期限切れなど)、ユーザーにエラー内容を報告する

## 14. 枠ごとのリマインド(投稿時刻が近づいたら実行。昼枠は毎日11:00、夕方枠は毎日17:00)

対象日は実行日と同じ日(今日)。対象枠(昼または夕方)について、`state/pending_drafts/{今日の日付}-{対象枠}.md` が存在し、かつ対応する `state/approved_drafts/{今日の日付}-{対象枠}.md` にまだ移動していない(=未承認の)場合のみ、その本文をチャットに再掲し、「今日{対象枠(12:00または18:00)}に投稿される予定です。お手すきのタイミングでOKをもらえますか?」とリマインドする。すでに承認済み、またはそもそもドラフトが存在しない場合は何もせず静かに終了する。

朝のあいさつ投稿のリマインドは別枠(前日夜23:00、`MORNING_GREETING.md` のタスクC)。

## 15. トークン期限について

`THREADS_ACCESS_TOKEN` は60日で失効する。エラーで投稿に失敗した場合、トークン切れの可能性が高いのでユーザーに再取得を促すこと(自動更新は未実装、v2で検討)。
