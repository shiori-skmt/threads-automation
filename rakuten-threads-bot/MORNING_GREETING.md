# Threads 朝の挨拶投稿パイプライン(毎朝6時投稿・PR/つぶやきとは別枠)

このファイルは、スケジュール実行されるClaude Codeセッションが**会話の記憶を一切持たない状態**で読む指示書です。省略せず記載しています。

作業ディレクトリ: このリポジトリの `rakuten-threads-bot/` フォルダ(相対パスで扱う)

この投稿は「おはようございます」+前向きな一言(たまに小さなTips)という、`PIPELINE.md` のPR型・つぶやき型とは別枠の固定コンテンツ。商品紹介やアフィリエイトは一切含めない。

**投稿は6時に自動で行いたいが、内容の確認はユーザーが仕事中の時間帯(前日15時頃)に行いたい**、という運用のため、3つの独立したスケジュールタスクに分かれている:

- **タスクA(毎日15:00実行)**: 翌朝分のドラフトを作成し、チャットに提示して承認を待つ。**投稿はしない**
- **タスクC(毎晩23:00実行)**: タスクAのドラフトがまだ未承認なら、寝る前に一度だけリマインドする。**新規に文章を作らない。投稿もしない**
- **タスクB(毎朝6:00実行)**: 承認済みの「今日分」ドラフトがあれば、それをThreadsに投稿する。未承認なら見送ったことをユーザーに知らせる。**新規に文章を作らない**

どのタスクが実行されているかは、呼び出し元のスケジュールタスクの指示(下記A/B/Cどのセクションを実行するか)で判断する。

**「今日」「翌朝分」などの日付は、すべて日本時間(JST, UTC+9)基準で決めること(必須)。** クラウド環境はUTCで動くため、生の日付をそのまま使うとJST早朝(0〜9時台)は前日扱いになってしまう(検証済みの不具合)。作業開始時に一度、次のコマンドでJST日付を取得し、以降の日付計算はすべてこの値を基準にする:
```bash
TZ=Asia/Tokyo date +%Y-%m-%d
```

**状態の永続化(git pull/push、必須)**: このパイプラインはクラウドで毎回新しくリポジトリをクローンして動く。作業開始時に必ず `git pull` してから読み始めること。`state/` 配下を1つでも変更したら、その都度リポジトリのルートで `git add rakuten-threads-bot/state && git commit -m "update state: ..."`、続けて `git pull --rebase`、`git push` を実行する(push失敗時はpull --rebase後に再push)。

## 状態管理フォルダ

- `state/morning_greeting/pending/{YYYY-MM-DD}.md`: 承認待ちドラフト(ファイル名の日付 = 投稿予定日)
- `state/morning_greeting/approved/{YYYY-MM-DD}.md`: 承認済み・投稿待ち(6時タスクが見に行く場所)
- `state/morning_greeting/posted/{YYYY-MM-DD}.md`: 投稿済みアーカイブ

## タスクA: ドラフト作成(毎日15:00実行、投稿はしない)

1. 対象日(投稿予定日)を「実行日の翌日」の日付(YYYY-MM-DD)とする
2. `state/morning_greeting/pending/{対象日}.md` または `state/morning_greeting/approved/{対象日}.md` が既に存在する場合、二重作成を避けるため何もせず終了する
3. 内容を作る:
   - ベースは「おはよう」の一言+前向きな気持ち(今日も頑張ろうと思える、ペルソナ(30代・子育て中・犬を飼っている女性)らしい朝の実感)。子どもを指すときは「ムスメ」と表記する
   - **天気・季節ネタにする場合は、ドラフトは前日15時時点の予報に基づくため外れる可能性がある(実例: 曇り予報が当日晴れだった)。断定的に書かず、タスクBで投稿直前に再確認される前提にする。また、投稿前に必ず東京の実際の天気を確認し、内容と齟齬が無いようにする**(例: `curl -s "https://api.open-meteo.com/v1/forecast?latitude=35.6895&longitude=139.6917&current_weather=true"`)。確認できない/合わない場合はこのテーマを避ける
   - 約4回に1回程度(25%程度)の頻度で、末尾に小さなTipsを添える。Tipsは犬のお世話・子育て・家事などのちょっとしたコツで、**商品名・ブランド名・アフィリエイトリンクは一切含めない**。残りの回はTips無しで前向きな一言のみ
   - 基本は1投稿で書き切る。内容量的にスレッド化が必要になることはほぼ無い想定
4. **厳守事項(PR投稿・つぶやき投稿との混同を避けるため)**:
   - 商品名・ブランド名・アフィリエイトリンクを一切含めない
   - 「PR」「#PR」表記を付けない
   - 購入や来店を促す表現を使わない
5. **自然さのルール(`PIPELINE.md` のつぶやき型と共通)**:
   - 二人称に「あなた」を使わない。子どもは「ムスメ」と表記する
   - ペットの反応などを、その場にいたか怪しい作り話っぽい描写で足さない
   - **文末には必ず絵文字か記号(「…」「〜」「!」「?」)を入れる**(何もつけずに終わらせない)。比率の目安は絵文字7割・記号3割程度
   - **改行・空行**: 1文ごとに機械的に空行を入れず、同じ話の流れ(同じ出来事の続き)はまとめて改行のみ、別の出来事・場面に移るところにだけ空行を入れる
   - **文脈の切れ目をまたぐときの前置き**: 空行の後は「そういえば」「あ、」「でもさ」「そうそう」のような自然な接続語を添える(毎回同じ言葉を使い回さない)
6. **人間らしさのルール(`PIPELINE.md` 8節「役割4.5: 人間らしさ推敲役」と共通。あいさつ投稿は特にAIっぽさが出やすいので念入りに)**:
   - 説明しすぎない。読者が文脈で分かる部分は言葉にせず余白を残す
   - **主語・目的語を省きすぎない**: 「余白を残す」は説明を足しすぎないという意味で、誰が何をしたか(主語・目的語)が読み取れなくなるほど省くのは禁止。特に「〜の途中で呼んだ」「〜してくれた」のように、読者が『誰が?誰に?』と迷う文は、主語を補うか、言い回しを具体的な場面に置き換える
   - **【2026-10-06追加】不自然さを生む5つのパターンを避ける**(実例: 「今日もゆずに起こされました、毎回同じ時間に鼻先でツンツンしてくるのが地味に効くんですよね😅 そういえば…ひと伸び…見てるだけで笑っちゃいます😂」が不自然と指摘された)
     1. **同じ場面の続きに「そういえば」「あ、」等の話題転換の前置きを使わない。** 前置きは「別の出来事・時間・場面」に移るときだけ
     2. **「〜んですよね」「〜ですよね」など、読者に同意を求める語りにしない。** 日記・独り言として言い切る
     3. **感情を説明しない。** 「見てるだけで笑っちゃいます」のように反応を言い直さず、「たまらん♡」「癒し」のように短く直球で言う。「地味に効く」のような、何に対する何なのか分からない言い回しも避ける
     4. **誰にでも当てはまる「あるある」だけで終わらせない。** 今の本人にしか言えない固有の事実(`recent_facts.md` に書かれた最近の様子)を必ず1つ入れる。`recent_facts.md` に無いことは作らない。使える事実が無い場合は、無理に足さず短く終える
     5. **文末と文の形を揃えない。** 全文を同じ敬体・同じ長さ・同じ「〜です😂」で並べず、短い独り言(「〜なーーー！」など)で終えてよい。まとめの一文は付けない
   - 文の長さ・リズムを揃えない。短文と長文を自然に混ぜる
   - 「重要です」「頑張りましょう」のような抽象的な言い回しより、具体的な場面・情景で語る(例: 「今日も頑張ろう」だけで終わらせず、その日の空気感や小さな出来事を添える)
   - 綺麗にまとめすぎない。毎回同じような締め方(「〜な一日にしましょう」等)を繰り返さない。余韻だけ残して終わってよい
   - **書き終えたら一度読み返し、「AIが書いたっぽい」語尾・言葉選び・テンポだけを抽出して人間らしく直す(このステップは省略しない)**
7. チェッカー: 以下をすべて満たすまで書き直す
   - [ ] 商品名・アフィリエイトリンク・「PR」表記が一切無いか
   - [ ] 購入や来店を促す表現が無いか
   - [ ] 薬機法・景品表示法に抵触する表現が無いか
   - [ ] 500字以内か
   - [ ] ペルソナとして自然か、個人・場所が特定される情報を含んでいないか
   - [ ] 二人称「あなた」を使っていないか
   - [ ] ペットの反応など作り話っぽい描写を足していないか
   - [ ] 6のAIっぽさ推敲パスを通したか
   - [ ] 文末が毎回絵文字か記号で終わっているか、絵文字7割・記号3割程度の比率になっているか
   - [ ] 各空行が本当に「別の出来事・場面への切り替わり」になっているか(実際に1つずつ検討する)
   - [ ] 空行の直後の文に自然な前置き(「そういえば」「あ、」等)が入っているか
8. `state/morning_greeting/pending/{対象日}.md` に保存する(投稿予定日・本文・Tipsの有無を明記)
9. ユーザーにチャットで内容をそのまま提示し、「これでOKか、修正したい点はあるか」を尋ねて**このセッションは終了する(絶対に投稿しない)**

## タスクC: 前夜リマインド(毎晩23:00実行、新規作成・投稿はしない)

**このタスクはあいさつ投稿(このファイル)専用。** 昼枠・夕方枠(`PIPELINE.md`)は投稿時刻がもっと早い(12:00/18:00)ため、別の時刻(昼枠11:00/夕方枠17:00)に専用のリマインドタスクがそれぞれ動いている。

1. 明日の日付(実行日の翌日、YYYY-MM-DD)を対象日とする
2. `state/morning_greeting/approved/{対象日}.md` が既に存在する場合(=すでに承認済み)、何もせず静かに終了する
3. `state/morning_greeting/pending/{対象日}.md` が存在する場合(=タスクAが作成したがまだ未承認)、その本文をチャットに再掲し、「明日の朝6時に投稿されるあいさつ文です。寝る前にOKをもらえますか?」と一言添えてリマインドする
4. `state/morning_greeting/pending/{対象日}.md` も存在しない場合(タスクAが未実行・失敗した可能性)、その旨を簡潔にユーザーに知らせる

8. **不自然さ最終チェッカー(必ず最後に実施)**
- [ ] **【不自然さ最終チェッカー(2026-10-06追加・必ず最後に実施)】** 下の5項目をすべて確認し、1つでも当てはまれば書き直してから出す:
  1. 同じ場面の続きに「そういえば」「あ、」等の前置きを使っていないか(別の出来事・時間・場面への切り替わりの時だけに限る)
  2. 「〜んですよね」「〜ですよね」のように同意を求める言い方になっていないか
  3. 感情を説明していないか(「見てるだけで笑っちゃう」など)/何に対する何なのか分からない言い回し(「地味に効く」など)が無いか/主語・目的語が抜けて「誰が?」と迷う文が無いか
  4. 誰にでも当てはまるあるある話だけになっていないか(`recent_facts.md` の固有の事実が1つ入っているか。無い場合は作り話を足していないか)
  5. 文末・文の長さ・敬体がすべて同じに揃っていないか/まとめの一文が付いていないか

## タスクB: 投稿(毎朝6:00実行)

1. 今日の日付(YYYY-MM-DD)に一致するファイルが `state/morning_greeting/approved/` にあるか確認する
2. **無ければ**、`state/morning_greeting/pending/{今日の日付}.md` が残っていないか確認し、以下のように知らせて終了する(新規に文章を作ったり投稿したりはしない):
   - pendingファイルが残っている場合:「昨夜分のあいさつ投稿はまだ承認されていなかったため、今日は見送りました。次はリマインド(23時)の時点でOKをお願いします」
   - pendingファイルも無い場合:「昨夜分のあいさつドラフトが作成されていなかったため、今日は見送りました」
2.5. **天気ネタの再確認(投稿直前・必須)**: 承認済みあいさつ本文に天気・気温・季節感の言及(晴れ/雨/曇り/暑い/涼しい/上着/傘/洗濯物など)がある場合、投稿直前に東京の実況・当日予報を取得して照合する:
   ```bash
   curl -s --max-time 20 "https://api.open-meteo.com/v1/forecast?latitude=35.6895&longitude=139.6917&current_weather=true&daily=weather_code,temperature_2m_max,precipitation_probability_max&timezone=Asia%2FTokyo&forecast_days=1"
   ```
   本文と食い違う場合(例: 「曇り」と書いたが晴れ)は**投稿せず**、食い違いの内容をセッションの最終メッセージに明記して終了する(勝手に書き換えて投稿しない。ユーザーの修正承認を待つ)。取得に失敗した場合は、`--max-time 15` で最大3回まで再試行する(各回を独立したBash呼び出しにする)。それでも取得できない場合は、本文の天気表現が**気温・降水確率などの数字や、晴れ/曇り/雨の断定を含まない、あいまいな書き方**(例: 「あたたかくなりそう」「朝はひんやり」)であれば、そのまま投稿してよい。数字や断定を含む場合は投稿せず見送る。
3. あれば、PIPELINE.mdの「0. 認証情報の読み込み」と同様にプロンプト中の認証情報をexportした上で、Threads Publishing APIでテキストのみの単独投稿をする。**curlコマンドを直接実行すること。Pythonなどのスクリプトファイルを生成して実行しないこと**(ブレース+クォートの組み合わせが「難読化っぽいパターン」として自動モードの安全確認に引っかかり、バイパス権限モードでも止まってしまうため)。**1回のBashツール呼び出しに複数のcurl・jqなどを`;`や`$()`でつなげて詰め込まないこと。「作成のcurl」「creation_idの取り出し」「公開のcurl」は、それぞれ独立したBashツール呼び出しに分ける**。curlには `--max-time 20` を付ける:
   ```
   POST https://graph.threads.com/v1.0/{THREADS_USER_ID}/threads
     ?media_type=TEXT&text={本文}&access_token={THREADS_ACCESS_TOKEN}
   ```
   → 返ってきた `id`(creation_id)を使って公開:
   ```
   POST https://graph.threads.com/v1.0/{THREADS_USER_ID}/threads_publish
     ?creation_id={creation_id}&access_token={THREADS_ACCESS_TOKEN}
   ```
4. 投稿成功後、`state/morning_greeting/approved/{今日の日付}.md` を `state/morning_greeting/posted/{今日の日付}.md` に移動する
5. ユーザーに一言報告する(例:「今朝のあいさつ投稿を公開しました」)
6. 投稿に失敗した場合(トークン期限切れなど)、ユーザーにエラー内容を報告する。`THREADS_ACCESS_TOKEN` は60日で失効するため、その可能性が高ければ再取得を促す

## 承認後のキュー登録(ユーザーがタスクAのドラフトにOKを出した時に実行)

これはタスクA・タスクBどちらのスケジュール実行でもなく、ユーザーが `state/morning_greeting/pending/` のドラフトに対して「OK」または修正指示を返信したときに、その場で(会話の続きとして)実行する:

1. 修正指示があれば、それを反映してから進める
2. `state/morning_greeting/pending/{対象日}.md` を `state/morning_greeting/approved/{対象日}.md` に移動する
3. ユーザーに「{対象日}の朝6時に投稿されるようキューに登録しました」と報告する。**この時点でも投稿はしない**(投稿はタスクBが6時に行う)
